# Business rules: where each one lives

The proposal's third edition lists 32 business rules (section 14). This table shows where each is
enforced on the server and which automated test proves it. "Ledger", "API", "Concurrency", "Offers"
and "Third edition" refer to `tests/ledger.test.ts`, `tests/api.test.ts`,
`tests/concurrency.test.ts`, `tests/offers.test.ts` and `tests/third-edition.test.ts`.

"Schedules" and "Brief" refer to `tests/kitar-collections.test.ts`,
`tests/kitar-collector-schedule.test.ts` and `tests/tomorrow.test.ts`.

## Decisions the proposal left open

These are choices made in code. Each should be confirmed, or changed, before a pilot.

| Question | What the code does | Where |
| --- | --- | --- |
| How does a shop's money reach the float? | A shop pays into its own **reward pool** in advance. An admin records the transfer (with a unique bank reference) once it shows in the trust account. Points and their fee are taken from that pool as they are given. | `ledger/finance.ts → recordMerchantDeposit` |
| What if a shop's pool is empty? | The sale is still recorded, but **no points are given** and the cashier is told why. | `merchant/service.ts → completeSale` |
| How is a fee that is not a whole sen rounded? | Half up to the nearest sen, per sale (20 points → 3 sen). | same |
| What if the float holds more than "points residents hold"? | It also holds money owed to shops this week and pools not yet given out. The check is float = points held + owed to shops + pools + community pool. | `ledger/finance.ts → floatPosition` |
| Is the service fee returned on a refund? | No. The points go back to the shop's pool; the fee for the original issue is kept. | `refundSale` |
| What if refunded points were already spent elsewhere? | Whatever the resident still holds is taken back. The shortfall is shown to the cashier to deduct from the cash refund. | `refundSale` |
| What if spent points are refunded after the shop was already paid for them? | The value comes from what the float still owes that shop, then from the shop's pool. If neither is enough the refund is refused until the shop tops up. | `refundSale` |
| Which points are spent first? | The batch that expires soonest. | `ledger/points.ts → consumeLots` |
| Do sponsor campaigns also pay the 15% issuance fee? | No. Sponsors pay the campaign fee (default 25%) and running costs (15%) up front, as in the proposal's example 3. | `campaigns/service.ts → fundCampaign` |
| How are SDP community programmes funded? | As a campaign with no sponsor, with the whole budget as reward pool by default. | console → Campaigns |
| Where do balance corrections come from? | The community pool, which SDP pays into. A correction is refused if the pool cannot cover it. | `decideAdjustment` |
| What happens when the float check fails? | All earning and spending pause. An SDP HQ admin resumes them under Rules. | `runFloatCheck`, `assertNotPaused` |
| When does a Lapor report earn XP? | When staff move it to "in progress" or "resolved", never on submission. | `reports/service.ts → updateReport` |
| What happens to points when an account is deleted? | They are given up and the value returns to whoever funded them. | `identity/service.ts → deleteAccount` |
| Danger line at 90% | The proposal gives 75% for Warning. 90% for Danger is our own demo rule; both are editable. | `program_settings` |
| Where do offer-backed points live? | Outside the double-entry ledger, in `offer_point_lots`, because no cash stands behind them. They never touch the float, and the float check is unchanged. | `offers/service.ts` |
| Can a Shop Offer be paid partly with cash-backed points? | No. An offer is paid with offer-backed points only; cash-backed points can still cover up to 30% of the rest of the bill. | `merchant/service.ts → createSale` |
| How many live offers per shop? | One at a time, so the cashier has a single switch. Pause or end it to create another. | unique index `shop_offers_one_live_idx` |
| Does a paused offer still count towards the month's pledge? | Yes. A shop's promise for a month is fixed once made, because residents may already have earned points against it. | `offer_pledges` |
| How is a success fee collected? | From the shop's reward pool, else from what the float owes it that week, else carried and collected at the next top-up or settlement (the proposal's net weekly statement). | `collectDueOfferFees` |
| Is the success fee returned on a refund? | No, as with the issuance fee. The offer points come back as offer points and the discount returns to the shop's budget for that month. | `returnOfferPoints` |
| Do offer-backed points expire? | Yes, under the same 12/24-month rule as every point. Nothing goes back anywhere: no cash stood behind them. | `expireOfferPoints` |
| Which actions earn offer-backed points? | Only those checked by something stronger than the resident's word: a signed machine session, a tracked trip, a garden code scan. Typed kiosk weights and QR-only loops earn XP and campaign points as before. | `recordAction` `offerEligible` |

| What does rain or a resident's report count for in Banjir? | Each can support a Warning as a second signal; neither can declare Danger. Danger needs the drain sensor and the camera to agree. | `assessZone` |
| What if a one-signal Warning draft is not answered? | It is not sent by itself; the township admins are told once. A one-signal Danger is sent after 3 minutes only if the water is still rising. A draft whose signal has gone stale is dropped. | `runAgentClock` |
| What is X, the rate-of-rise line? | 15 cm in 10 minutes by default, editable per sensor. The annex leaves it to the site survey. | `flood_sensors.rise_cm_10min` |

| What is the warning lead time? | Minutes from the event's first alert to its first danger alert. An event that started at danger has a lead time of 0. | `banjir/events.ts` |
| How are the simulated sensors driven? | The console slider sets their level; the agent clock makes them report every 60 seconds (15 above the warning line), signed with their own keys, through the same `storeReadings` as a real device. | `banjir/sensors.ts → simulatedHeartbeat` |

| Who can operate the gate? | Guards, and township staff and admins covering a shift. | `tamu/routes.ts` |
